# Orbital model and provenance

The orbital module integrates four point masses (Jupiter, Io, Europa and Ganymede) using double-precision velocity Verlet. Positions are kilometres, velocities kilometres per second and gravitational parameters km³/s². Time is SI seconds relative to the initial epoch. The integrator is reversible and symplectic for its autonomous point-mass equations; choose and verify a suitable timestep for the case under study.

Initial geometric Cartesian states were obtained from [NASA/JPL Horizons](https://ssd.jpl.nasa.gov/horizons/), with targets 501, 502 and 503, centre `500@599` (Jupiter centre), epoch JD 2460676.5 TDB (2025-01-01 00:00:00 TDB), ICRF reference frame, `REF_PLANE=FRAME`, `VEC_TABLE=2`, and `OUT_UNITS=KM-S`. Horizons identified the source as `jup365_merged`. Jupiter's initial relative state is zero; all four states are then translated into their own centre-of-mass frame, which leaves all relative vectors unchanged. GM values come from JPL's [planetary satellite physical parameters](https://ssd.jpl.nasa.gov/sats/phys_par/) (JUP365).

The initial conditions are from an ephemeris, but subsequent results are **not JPL ephemerides**. This simplified model omits Callisto, the Sun, Jupiter's oblateness, tides, dissipation, body rotation, relativity and all tidal back-reaction. These omissions especially affect the resonance and long-term trajectories. Do not use this model for mission navigation or infer validated long-term predictions from it.

Europa's displayed osculating semi-major axis and eccentricity are derived from the instantaneous Jupiter-relative state and their combined GM. The Laplace angle is the wrapped angle λIo − 3λEuropa + 2λGanymede, using osculating mean longitudes in ICRF. It is a diagnostic, not a claim of libration. Energy and angular momentum diagnostics use GM as the mass weight (physical totals multiplied by G), allowing meaningful relative conservation checks without selecting a numerical G.

Editing Europa's eccentricity or semi-major axis reconstructs a consistent bound two-body osculating ellipse at the initial true anomaly and orbital-plane orientation, then re-centres the four-body system. This is a new hypothetical state, not an ephemeris observation. A changed initial orbit invalidates existing integration results.

An untouched new run begins with the stored Horizons state without reconstructing it from rounded display values. A run with an edited initial element is hypothetical. A checkpoint restored from disk is user-supplied data; validation checks its structure and model constants, but cannot prove that its positions or history were produced by this solver. Exports and subsequent checkpoints identify restored data as imported and unverified. Existing valid version-1 checkpoint files remain loadable.

Version-1 checkpoints do not record which initial parameters were explicitly edited. For a new run after loading one, a value exactly equal to the epoch default is treated as a default; any differing value remains an override. This inference does not establish the origin of the imported checkpoint.

CPU version-3 and version-4 checkpoints carry a SHA-256 checksum over a canonical representation of the checkpoint payload, including its model, epoch, and solver identifiers. The app verifies it before loading and rejects missing or mismatched checksums. A matching checksum detects accidental changes; anyone who edits a file can recompute it, so it does not authenticate its source or verify its scientific results. Version-1 and version-2 CPU checkpoints remain loadable without checksum verification and are labeled accordingly. A changed version field can make a file indistinguishable from a legacy checkpoint, so compatibility also prevents detection of every possible version change. Exports are separate documents and do not carry the checkpoint-only checksum.

Tests cover initial values, edits, reversibility, a two-body circular orbit, four-body conservation, and timestep refinement. These are numerical checks of the stated simplified equations, not scientific validation of the full Europa system.

The orbital workspace displays Jupiter-relative positions and recent trajectories from the active simulation, projected in an interactive 3D view. Body sizes are exaggerated and are not part of the numerical model. CPU and GPU runs are separate; the GPU view uses only samples that have passed the independent CPU comparison gate. Osculating eccentricity, semi-major axis and the wrapped Laplace angle are plotted against physical simulation time. A break at the angle wrap prevents a false line across the ±180° boundary.

The conservation indicators report the absolute change in mass-weighted energy divided by the magnitude of its baseline, and the magnitude of the angular-momentum vector change divided by the baseline vector magnitude. Baselines are recorded at the beginning of a new run. Older checkpoints do not contain those values or historical body positions, so a restored-state baseline is established for subsequent results and unavailable history is not reconstructed. CPU version-4 and GPU version-5 checkpoints preserve the new analysis history and baseline; version-1 through version-3 CPU and version-4 GPU checkpoints remain supported. These are numerical checks, not proof of physical validity. Histories retain up to 2,000 samples and imported values remain unverified.
